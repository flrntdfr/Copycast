Validation (field validators raise `ValueError` with a one-line message naming the key; cross-field checks use `@model_validator(mode="after")` on `AuthSettings`, then `Settings`):

| Rule | Message (prefix `invalid configuration: auth…`) |
|---|---|
| `users[i].username` matches the pattern | `auth.users[i].username must be 1-32 lowercase letters, digits, '.', '_' or '-', starting with a letter or digit` |
| `username` (legacy) | **unchanged from 2.3.0** (non-blank, no `:`). When `legacy_owner` differs from the stripped, lower-cased name, startup logs `auth.legacy_owner_normalised from=… to=…` once (§6 A4). |
| `users[i].password_hash` starts with `$argon2id$` and `argon2.extract_parameters()` accepts it | `…password_hash must be an argon2id PHC string (run: copycast users hash-password)`. A plaintext password lands here. |
| `totp_secret` decodes as base32 and has at least 16 characters | `…totp_secret must be base32 (run: copycast users totp)` |
| quotas parse (`domain.quota.parse_quota_limit`) | `…quota must be like "10 GB", "500 MB" or "unlimited"` |
| usernames are unique | `auth.users: duplicate username "x"` |
| at least one admin when `users` is non-empty | `auth.users: at least one user needs admin = true` |
| `password` and `users` are exclusive | `auth.password and auth.users are exclusive: remove COPYCAST__AUTH__PASSWORD` |
| users mode: `owner_of_existing`, if set, names a configured user | `auth.owner_of_existing names no configured user: "x"` |
| legacy/open mode: `owner_of_existing`, if set, equals `legacy_owner` | `auth.owner_of_existing must be auth.username without auth.users` |
| users mode with a global `[engine.options] cookiefile` (a `Settings` model validator) | `engine.options.cookiefile cannot be set with auth.users (each user has their own Cookie files)` |

More settings rules:
- **Env JSON.** `COPYCAST__AUTH__USERS='[{"username":"…","password_hash":"…","admin":true}]'` works through pydantic-settings' complex-value decoding. An env list **replaces** a TOML list; it never merges with it. Test this.
- **TOTP on https is not a startup error.** It is enforced at login (§3.4).
- **`redacted()`** masks `auth.users[*].password_hash` and every non-null `auth.users[*].totp_secret` as `"***"`, in addition to today's fields.
- **`config/copycast.toml`** gains a commented `[auth]` example with `default_quota`, `session_days`, `owner_of_existing` and two `[[auth.users]]`.


Legacy mode:
- `UserDirectory` hashes `auth.password` with `PasswordHasher()` **lazily, on first use** (a `functools.cached_property`).
- From then on every login, the legacy one included, runs exactly one argon2 verify. This keeps the timing of the unknown-user and wrong-password answers equal.
- `sync_users` computes it at startup, on the hash limiter, so no request ever hashes on the event loop; `get_me` uses `has_totp`, which never touches it (3.0-foundation.1).
- The operator password reaches Postgres only as that salted argon2 hash (`users.credential_digest`); a database reader cannot crack it at SHA-256 speed (3.0-foundation.1).

### 1.5 Sessions and login (`src/copycast/application/services/auth.py`, new)

```python
LOCK_THRESHOLD: Final = 5            # failures before the first lock
LOCK_BASE_SECONDS: Final = 30        # 30 s, doubling each further failure
LOCK_MAX_SECONDS: Final = 900
SESSION_TOUCH_SECONDS: Final = 60    # last_seen_at/expires_at are written at most once a minute

@dataclass(frozen=True, slots=True)
class IssuedSession:                 # internal: never a ReadModel, never in OpenAPI
    token: str
    expires_at: datetime

@capability("login", request=LoginRequest)
async def login(ctx: ServiceContext, body: LoginRequest, *, user_agent: str | None = None) -> IssuedSession
@capability("logout")
async def logout(ctx: ServiceContext, token: str | None) -> None             # idempotent
@capability("get_me", response=MeRead)
async def get_me(ctx: ServiceContext) -> MeRead
@capability("authenticate_session")
async def authenticate_session(ctx: ServiceContext, token: str) -> Principal | None
async def sync_users(ctx: ServiceContext) -> None     # startup; not a capability
```

- **argon2 runs on its own limiter.** `services/auth.py` holds a module-level `HASH_LIMITER = anyio.CapacityLimiter(HASH_SLOTS)` with `HASH_SLOTS: Final = 2` (2 × 64 MiB at the default parameters), and every verify, `dummy_verify` included, runs through `anyio.to_thread.run_sync(fn, limiter=HASH_LIMITER)`. It never uses the default thread limiter, which FastAPI's sync dependencies and `FileResponse` share.
  - At most `HASH_QUEUE_MAX: Final = 16` logins may wait for a slot. A login that finds the queue full, or waits longer than `HASH_WAIT_SECONDS: Final = 5.0`, raises `LoginBusy` (503, `Retry-After: 5`) **before** any verify and without touching `login_attempts`. The rule is the same for every name, so it is no oracle.
  - There is no per-IP limit (§6.1); this bounds memory and CPU per process whatever the flood.
- **The lock check is atomic with the count (3.0-foundation.1).** Holding its hash slot (`hash_slot()`), a login first calls `login_attempts.claim(key, now)`: the row is created if needed and read `FOR UPDATE`; a locked name is refused with nothing counted (dummy verify, `LoginLocked`); otherwise the attempt is counted as a failure **before** its verify, and from the threshold on the lock is set at once. A success `reset`s the row. So a burst of guesses, from any number of api processes, never verifies more than the threshold's worth (it used to verify every request already past the check, up to `HASH_SLOTS + HASH_QUEUE_MAX` per process).
- **Unknown names are never stored in clear (3.0-foundation.1).** The `login_attempts` key of a typed name that is no User is `"?" + HMAC-SHA256(instance secret "login-attempts", typed)[:32 hex]`, so throttling stays uniform across processes while a password typed into the username field is unreadable. Logins also prune stale rows every `PRUNE_EVERY_SECONDS` (600), not only at startup.
- `sync_users` does five things:
  1. `INSERT … ON CONFLICT DO NOTHING` of every `UserDirectory.users()` row. It **never deletes** users.
  2. For each configured user, compares `users.credential_digest` with `UserDirectory.credential_digest(username)`. When it differs (a new password hash or TOTP secret, or the first start of 3.0), it deletes that user's sessions, clears `totp_last_step` when the TOTP secret changed, and stores the new digest. **Replacing a password signs out every session of that user** at the next restart.
  3. `DELETE FROM sessions` for usernames that are not configured.
  4. `DELETE FROM sessions WHERE expires_at < now()`.
  5. `DELETE FROM login_attempts WHERE (locked_until IS NULL OR locked_until < now()) AND updated_at < now() - interval '24 hours'`.
- After `sync_users`, in users **and legacy** mode (3.0-foundation.1), startup logs one `auth.removed_owner_has_feeds` **warning** per owner that still owns Feeds but is not configured, with the Feed count and the hint `copycast users reassign <owner> <new>` (users mode) or `set auth.username back to <owner>, or run: copycast users reassign <owner> <legacy_owner>` (legacy mode) (§3.3).
- `sync_users` is called by the api lifespan and the worker start, after migrations and before `ensure_default_bucket`.

```python
PRINCIPAL_STATE_KEY: Final = "principal"
def requires_principal(path: str) -> bool    # True for /api and everything under /api/ only
                                             # (/auth/logout answers 204 without a session, §1.11)

    def __init__(self, app: ASGIApp, *, container: ApiContainer) -> None
    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None
```
How a request's Principal is resolved (HTTP scopes only):
1. Open mode: `users.open_principal()` on every path, with no database access.
2. Otherwise, a session cookie, when present on **any** path, resolves through `container.services.authenticate_session(token)`, which runs as SYSTEM.
3. Otherwise (no cookie, **or a cookie that resolved to None**), `Authorization: Bearer cck_…` resolves only on paths under `/api/`, through `authenticate_api_key`. The result is a Principal with `via=api_key`, the key's `api_key_id` and `key_scope`, and the admin flag from the directory. A key whose owner is not configured resolves to None.
4. The result goes into `scope["state"]["principal"]`, which may be None.
5. If `requires_principal(path)` and the Principal is None, the answer is **401 problem+json, slug `unauthorized`, with no `WWW-Authenticate` header**, and `Cache-Control: no-store`.

The middleware gates nothing else. These stay open: `/healthz`, `/robots.txt`, the SPA shell, `/assets/*`, `/login`, `POST /auth/login`, `/uploads/*`, `/art/*`, `/feeds/*` (behind `FeedAccess`) and `/mcp` (behind FastMCP's own verifier).

`get_services` checks Bearer keys on `/api`. When `principal.via == api_key`:
- the route's `x-capability` must be in `tool_capabilities()`, else `Forbidden`. Capability-less routes (`play_item_*`, `list_mirrors`, …) and TOOL_EXEMPT capabilities (`get_me`, key CRUD, cookies, defaults) therefore refuse keys;
- the key's scope must allow `full` for `DESTRUCTIVE` capabilities, `read` for GET/HEAD and `write` for the other methods, else `Forbidden`.
- **Argument-level scope checks live in the service layer**, not in the MCP tool bodies, so the route and the tool enforce them alike. F0 adds `application/services/keyscope.py`:
  ```python
  def require_key_scope(ctx: ServiceContext, needed: KeyScope, what: str) -> None
      # no-op unless ctx.principal.via == api_key; when ctx.principal.key_scope does not cover
      # `needed`: Forbidden(f"{what} needs an API key with scope '{needed}'; this key has scope
      # '{key_scope}'"), so the MCP text keeps today's "needs an API key with scope" wording
  ```
  and calls it, before any write, in: `mirrors.create_mirror` and `update_mirror` (backfill mode `rolling`, or `automatic` with expiry: today's `_check_deleting_mode` rule; a non-empty `engine_options`: today's `_check_engine_options` rule), `buckets.create_bucket` and `buckets.update_bucket` (`autoprune_days` set). `problems.py`: `domain_error_handler` adds `WWW-Authenticate: Basic realm="Copycast"` **only when the path starts with `/feeds/`**. `unauthorized_response` follows the same rule. `/api` and `/auth` never send the challenge.

- Open mode: allow.

### 1.15 Engine gateway: a cookie jar per call

`application/ports.py`:

Engine rules:
- `cookie_jar` is an Object store key, or None for no stored cookies.
- `YtDlpEngine` builds `StoredCookies(layout, scratch, key=cookie_jar)` per call. `cookie_scope` copies that jar into the call's Scratch file and writes rotated cookies back to **the same key**. The constructor-held jar disappears.
- An explicit `cookiefile` in `options` still wins. `[engine.options] cookiefile` remains possible only outside users mode (§1.2).
- **Quota estimate.** When `spec.max_bytes` is not None and the fetch is `FetchKind.ytdlp`, a match filter runs on yt-dlp's post-format-selection call:
  - it computes `size = filesize or filesize_approx`, summed over `requested_formats` when present;
  - when `size > max_bytes`, it records the size in `_HookState` and rejects the video;
  - `fetch_item` then raises `QuotaExceeded(size)`.
  - A missing size passes. Direct (RSS) fetches are never estimated.

`SourceGateway` (`context.py`) and `SourceGatewayAdapter` (`app.py`): every method gains a keyword-only `owner: str`:
- `probe(…, owner)`;
- `cached(*, token, url, owner)`: `mirrors._resolve_snapshot` reads the cache through it before probing, so it must be per owner too;
- `list_playlists(owner)`;
- `search_videos(…, owner)`;
- `inspect_video(…, owner)`;
- `list_shallow(…, owner)`.

The adapter calls the seam `cookie_jar_key(layout, owner)` (§1.17). `adapters/sources/probe.py::probe(…, cookie_jar: str | None = None, owner: str | None = None)` gains both arguments: it threads `cookie_jar` to `_ytdlp_entries`, which passes it to `engine.list_source(…, cookie_jar=cookie_jar)` (F0), and keeps `owner` (passed by `SourceGatewayAdapter.probe`, untouched until C2 keys `cache.put(entry, owner=owner)` on it; 3.0-foundation.1).

| Call | Owner whose cookies (and Defaults) are used |
|---|---|
| Refresh, archive, Request expansion, inspect/fetch_item_metadata, Light Refresh, update_mirror retarget probe | the **Feed's owner** (also when an Admin acts on it) |
| probe_source, create_mirror's probe, search_videos, list_youtube_playlists | the **acting User** (`ctx.principal.username`; for SYSTEM, `users.owner_of_existing`) |

## 2. Migration `0017_users_and_owners` and the Object store copy

### 2.1 Alembic `0017` (`adapters/db/migrations/versions/0017_users_and_owners.py`)

Style: like 0015 and 0016. A module docstring gives the intent and the upgrade and downgrade semantics. Revision variables are typed. Tables use `op.create_table` with `op.f()` names. Data steps are SQL string constants. `revision="0017"`, `down_revision="0016"`.

**Where the owner of existing rows comes from.** In compose the api and the worker start together and race for `MIGRATE_LOCK`, and `copycast migrate` and rebuild migrate too, so **every** caller must hand over the same owner:
- `ensure_schema(db_engine, *, owner_of_existing: str | None = None)` and `prepare_schema(db_engine, *, auto_migrate: bool, owner_of_existing: str | None = None)` put the value in `config.attributes["owner_of_existing"]` **only when it is not None**.
- The migration reads `context.config.attributes.get("owner_of_existing")` and, when it is None, falls back to `get_settings().auth.effective_owner_of_existing` (a plain `alembic upgrade`, or any caller that forgot). There is no hard-coded `"copycast"` default anywhere on this path.
- Explicit callers (F0 wires all of them, §1.17): `Container.prepare_schema()` (api lifespan), `worker/main.py` (`prepare_schema(container.db_engine, auto_migrate=…, owner_of_existing=settings.auth.effective_owner_of_existing)`), `cli.migrate` and `adapters/storage/rebuild.rebuild()` (`ensure_schema(engine, owner_of_existing=settings.auth.effective_owner_of_existing)`).
- The test template is migrated with `owner_of_existing="copycast"` passed explicitly (the open-mode Admin), so the template never depends on the environment.
- Test (F0, `tests/integration/storage/test_migrations.py::test_worker_first_migrates_with_owner_of_existing`): a database at 0016 with Feeds and a key; settings in users mode with `owner_of_existing="florent"` and no `copycast` user; run `worker.main`'s schema step (not the api's) first; assert every `feeds.owner` and `api_keys.owner` is `florent`. The same assertion for `copycast migrate` through `CliRunner`.

Upgrade, in order:

| # | Change | Detail |

### 2.2 The Object store copy (not Alembic; group C2)

**3.0 copies and never deletes.** The legacy keys stay where they are, so rolling the image back to 2.3.0 (§7, rollback) still finds its Defaults and Cookie files. A later release (3.1 or after) deletes them.

`src/copycast/adapters/storage/user_settings.py`:
```python
@dataclass(frozen=True)
class MoveReport: copied: list[str]; conflicts: list[str]; already_done: bool
MARKER_KEY: Final = "users/.legacy-settings-copied"   # JSON {"owner": …, "at": …, "copied": […]}
def migrate_legacy_settings(layout: Layout, owner: str) -> MoveReport
```
It runs from `Container.migrate_user_settings()` at **api lifespan start and worker start**, after `preflight` and before anything is served or claimed. An Object store error is fatal, like preflight.

For each legacy key:

| Legacy key | Target |
|---|---|
| `engine/defaults.json` | `users/{owner}/defaults.json` |
| `engine/cookies.txt` | `users/{owner}/cookies.txt` |
| `engine/cookies/{name}.txt` | `users/{owner}/cookie-files/{name}.txt` |

0. `MARKER_KEY` present: return `already_done=True` and touch nothing. Later edits under `users/{owner}/` are never overwritten by the stale legacy keys.
1. Source absent: nothing to do.
2. Target absent: copy (get + put). The source stays.
3. Target present: leave both, log `user_settings.migration_conflict` with the key names (never the contents), and add it to `conflicts`.
4. Write `MARKER_KEY` last.

Properties:
- The copy is idempotent: once the marker exists it is a no-op, and before that a re-run only re-copies equal bytes.
- Racing api and worker processes are safe: both copy the same bytes and write an equivalent marker.
- 2.3.0 never reads `users/`, so the copy is invisible to a rolled-back image. Changes made under 3.0 (new cookies, new Defaults) are lost on a rollback; the rollout says so (§7).
- `owner` is `users.owner_of_existing`.
- A legacy jar with no files becomes the per-user jar. The existing "legacy single jar shows as file `cookies`" logic of `_Store.keys()` carries over per user.
- `copycast rebuild` restores Postgres only. Defaults and Cookie files are read live from `users/{u}/`, so it needs nothing for them.

## 3. Behaviour rules

### 3.1 Auth modes

| | open | legacy | users |
|---|---|---|---|
| Trigger | no `auth.users`, no `auth.password` | `auth.password` only | `auth.users` non-empty |
| Principal | `Principal.open_admin(auth.legacy_owner)` on every request | session (login with `auth.username` and the password) | session or API key |
| `settings.auth.enabled` | False | True | True |
| `/api`, SPA, SSE | open, exactly as 2.3.0 | session | session |
| MCP | no verifier (as today) | API keys | API keys |
| Feed URLs and media keys | no pair (as today) | pair and `/k/{key}/` (as today) | the same |
| TOTP | — | not required (warns on https, §6 A2) | Admins on https: required |
| Quota | `default_quota` (default unlimited) | same | per user |
| Owner stamped on new rows | `auth.legacy_owner` | `auth.legacy_owner` | the actor |
| Operator pair on `/feeds` | — (no auth) | accepted, as 2.3.0 | **refused** (§1.6, §6.3) |
| New Mirror ids | `mirror_id(key)` | `mirror_id(key)` | `owned_mirror_id(owner, key)` (§3.2) |

- **Open mode is byte-for-byte 2.3.0.** The existing suite runs unchanged in it, except for the files that test legacy Basic on `/api` (§5.1).
- **D4.** Feed pairs, media keys, feed URLs and enclosure URLs stay byte-identical in every mode. `PublicUrlsAdapter(auth_enabled=settings.auth.enabled)` and the renderer's media key use the same predicate as today. Existing ids never change.

### 3.2 Visibility

- A Feed you cannot see answers **404 `not-found`, never 403**. The same holds for its items, requests, jobs, objects, events and uploads.
- `create_mirror` never reveals another owner's Feed:
  - `FeedExists` is raised only for the actor's own duplicate (`by_dedup_key(actor, key)`);
  - **id choice (changed from plan §4, §6 A31, accepted by the product owner 2026-11-06):**
    - **users mode:** every new Mirror and Capture gets `owned_mirror_id(actor, key)`, whether or not anyone else mirrors the Source. The first owner is not special, so alice's id is the same whether or not bob mirrors X, and comparing her id with `sha256(key)[:16]` reveals nothing;
    - **open and legacy mode:** `mirror_id(key)`, byte-identical to 2.3.0;
    - existing ids never change (D4), including the pre-3.0 unsalted ids of `owner_of_existing`;
    - the id is still checked with `exists_id`. The actor's own duplicate is caught earlier as `FeedExists`, so a hit here means a 64-bit hash collision. It raises `Conflict("feed id collision")` (409, no id, no owner); in practice it never happens, so it is no oracle.

  Captures follow the same rule, so two Users' Watch Later never collide.
- `_retarget` checks `by_dedup_key(feed.owner, new_key)` and keeps the id.
- **Admins** see and act on every Feed. They create as themselves. `FeedRead.owner` and `owner_removed` label others' Feeds.
- Admin-only capabilities answer **403 `forbidden`** to Members (role, not existence).
- **The default Local feed** is one per owner:
  - every configured user gets theirs at startup (`ensure_default_bucket(owner)` for each `users.users()`), so a new user gets one at the next restart;
  - deleting `is_default` is refused, as today;
  - `find_bucket("Copycast")` prefers the actor's own.

### 3.3 Removed users (in the database, not in the config)

- Their sessions are deleted at startup. Their API keys and feed pairs stop working; the uniform 401 and 404 answers stay the same.
- Their Feeds and objects stay. Admins see them with `owner_removed=true` and can act on them.
- The scheduler does not schedule Refreshes or autoprunes for their Feeds (filter `owner IN configured`). Light Refresh cannot happen, because their pairs fail.
- Their quota is `default_quota`. Adding the user back restores everything.
- **The mode-switch trap.** `owner_of_existing` applies once, in 0017. A self-hoster who upgrades in open or legacy mode gets their Feeds owned by `legacy_owner` (`copycast` by default). If they later switch to users mode without configuring that name, every Feed becomes "owner removed" and every feed pair and media key answers 401. Defence:
  - startup logs the `auth.removed_owner_has_feeds` warning (§1.5) for each such owner, with the Feed count and the exact `copycast users reassign <owner> <new>` command;
  - `docs/operations.md` ("Switching to users mode") and ADR 0027 describe the trap and the command;
  - nothing is reassigned automatically: data changes owner only by an explicit command (§6 A32).
- **The legacy rename trap (3.0-foundation.1).** The same happens without leaving legacy mode: renaming `auth.username` (2.3.0 allowed it freely), or setting `COPYCAST__AUTH__PASSWORD` with another `COPYCAST__AUTH__USERNAME` after an open-mode upgrade, changes `legacy_owner`, so every existing Feed's pair and media key and every existing API key answers 401 and every Feed shows `owner_removed`; `owner_of_existing` cannot help (it must equal `legacy_owner`). Defence: the same warning, logged in legacy mode too, with the hint `set auth.username back to <owner>, or run: copycast users reassign <owner> <legacy_owner>`; G documents it next to the mode-switch trap in `docs/operations.md` and ADR 0027.

### 3.4 Login, throttling and TOTP

0. If `base_url` is https and the request is not (`request.url.scheme`, which honours the forwarded headers of U11), raise `HttpsRequired` (400) before anything else. The browser could not store the `Secure` `__Host-` cookie on an http host name, so the login would otherwise "succeed" and silently not stick. The route passes the scheme to `login`.
1. Normalise the username (strip, lower-case).
2. Take a hash slot, then `claim` the attempt (§1.5): if the name is locked, run `dummy_verify` and raise `LoginLocked(retry_after)`; otherwise the attempt is counted now. This happens for unknown and known names alike (an unknown one under its HMAC key).
3. Look the user up in the directory (`login_name_matches`; in legacy mode the slug and the typed name both match, §1.4). Unknown: `dummy_verify`, then fail.
4. Verify the password with argon2, through `HASH_LIMITER` (§1.5). Every verify, real or dummy, takes a slot; when none frees up in time, the login raises `LoginBusy` without verifying and without recording a failure.
5. If the user is an Admin with `admin_login_refused` (users mode, https, no TOTP): fail and log `auth.login_refused reason=admin_without_totp`.
6. If the user has a TOTP key: `match_step`, then `claim_totp_step`. Both must succeed. A replayed code fails.
7. On any failure: nothing more to record (the claim counted it: 5 failures, then lock `30 s × 2^(n−5)`, capped at 900 s) and raise `LoginFailed`. Every failure answers the same 401 body.
8. On success: `reset`; **delete the session whose token came with the request, if any** (so an injected or stale cookie never survives a login); a new session (`mint_session_token`, `session_digest`); `touch_login`; `delete_expired`; then 204 with the cookie.

More rules:
- A TOTP code sent for a user without TOTP is ignored.
- **Lockout trade-off (ADR 0027).** The lock is per username, not per IP (Traefik shows one client address). Anyone who knows a username can keep it locked with one wrong attempt every 15 minutes. That is accepted for 3.0: a lock only delays, sessions that already exist are untouched, and an operator can clear it by deleting the `login_attempts` row. ADR 0027 states it.
- **Timing.** `dummy_verify` uses `PasswordHasher.slowest(...)` over every configured hash, so an unknown name never answers faster than a known one. Users whose hashes use weaker parameters than the slowest answer faster than an unknown name; startup warns when the parameters differ (`auth.hash_parameters_differ`), and `docs/operations.md` says to hash every password with the same `copycast users hash-password`.
- **The session slides.** `authenticate_session` writes `last_seen_at=now` and `expires_at=now+session_days` at most once a minute. `GET /api/me` re-issues the cookie.
- Roles are read from the config on every request, so a demotion applies at restart without touching the session.
- **Cookie:** `__Host-copycast_session` with `Secure` on https. On http it is `copycast_session` without `Secure`. Both have `HttpOnly`, `SameSite=Lax`, `Path=/` and `Max-Age`.
- **CSRF.** 2.3.0's `CrossSiteGuardMiddleware` stays outermost of the auth layers, unchanged, and covers `POST /auth/login` and `/auth/logout`. SameSite=Lax is defence in depth. A request with neither `Sec-Fetch-Site` nor `Origin` still passes (curl, Playwright `request`, MCP clients).

### 3.5 Quotas

- **Usage** is `SUM(feeds.storage_bytes) WHERE owner = u`. **States:** `ok`, `near` (≥ 90 %) and `over` (≥ 100 %).
- **Archive job** (`worker/jobs/archive_item.run`), after the not-wanted and Paused checks and before marking the item archiving:
  - if the owner's state is `over`: `quota.mark_blocked(item, quota, estimate_bytes=None)` and `uow.publish(ItemEvent(feed_id, item_id, state=wanted))` in the same unit of work; the job **succeeds** with `JobOutcome(result={"blocked": "quota"})`;
  - otherwise: `FetchSpec.max_bytes = remaining_bytes(owner)`;
  - an engine `QuotaExceeded(size)`: the item is blocked the same way with `estimate_bytes=size`, no attempt is counted, and there is no retry and no runner change.
  - **`StorageFull` is never reused for quota**, because it pauses archive claims for everyone.
- **A blocked item** keeps `archive_state = wanted` with `blocked_reason = quota` (and `blocked_bytes`):
  - `enqueue_archive_jobs` (`worker/jobs/common.py`) and Light Refresh `_enqueue_wanted` skip blocked rows. `items.enqueue_archive` itself stays check-free: a Light Refresh never raises `OverQuota`, so a podcast app's `GET /feeds/{id}.xml` always answers;
  - the Catalog shows "Over quota";
  - `catalog_state()` is unchanged.
- **Manual archive / retry.** Only the capability entry points check the quota, through the F0 seam `quota.gate_manual(uow, users, feed.owner)` (§1.17), called right after the Feed or item is required and **before** any `set_wanted`:
  - `archive_item` (manual, UI, MCP, and the `feed_fetch` trigger of a first play), `archive_available`, `retry_failed`, and `select_items` unless `dry_run`;
  - when the owner is over: `OverQuota` (507), and nothing was changed;
  - otherwise `on_manual_wanted` clears `blocked_reason` for the selected items right after `set_wanted`, and they enqueue as today.
  - `create_mirror` and `update_mirror` (selection Backfills through `_apply_selection`), Follow, Backfill and policy switches **never gate**: they queue as usual, and the archive job blocks what does not fit (D2).
- **Re-queue when usage drops** (no job storm):
  - a scheduler sweep every tick (60 s, `_due_unblocks`): for each `owners_with_blocked()`, `release_if_room(owner)` (§1.10). It releases nothing for an owner who is over; otherwise it walks at most `RELEASE_PER_TICK` (20) blocked items in priority order and releases only those whose `blocked_bytes` fit the remaining budget (items blocked with an unknown size, `blocked_bytes IS NULL`, are released while the owner is not over). It stops at the first item that does not fit;
  - an item blocked by `QuotaExceeded` therefore stays blocked, with **no job and no yt-dlp extraction**, until usage drops or the quota grows enough for its estimate;
  - also a fast path at the end of the prune job when bytes were freed (the same `release_if_room`).
  - This covers deletes, purges, Sync, expiry and a quota raised at restart.
- **Uploads:**
  - `create_upload` with `size_bytes` checks `require_room(owner, adding_bytes=size)` and raises 507 if it does not fit;
  - it stores `owner` and `declared_bytes` in `upload.json`;
  - `put_upload` (SYSTEM, token) stops at `min(MAX_UPLOAD_BYTES, remaining_bytes(owner))`. It discards the partial file and answers 507;
  - **`add_uploads` and `create_serial_bucket` call `require_room(owner, adding_bytes=sum(received size_bytes))` before copying anything**, and raise 507 for the whole call when the batch does not fit. Staging N uploads each just under the remaining quota and adding them at once therefore cannot overshoot. Staged uploads are not counted in usage (they expire within 24 h).
- **First play** of an unarchived Ephemeral item on `/feeds/…/media` (`public._archive_on_demand`):
  - SYSTEM `archive_item(…, trigger=feed_fetch)` raises `OverQuota` from `gate_manual` when the owner is over, which gives **507 `over-quota` without Retry-After**;
  - when the job blocks the item instead (`QuotaExceeded`), the `ItemEvent` it publishes wakes the wait; the loop checks `item.blocked_reason` on every pass, next to `media` and `failed`, and answers 507 at once rather than polling out its 50 s.
- **Overshoot.** A running job always finishes. Each archive job reads `remaining_bytes` when it starts, so with a worker concurrency of N the owner can overshoot by up to **N Episodes** (N parallel jobs of one owner each see the same remaining budget), plus RSS enclosures, which are never estimated. Per-owner admission is not serialised in 3.0 (§6.1). ADR 0029 and `docs/operations.md` use this wording, not "at most one Episode".
- **Untouched:** Backfill, Follow and policy switches queue as usual. Nothing is deleted on a user's behalf.

**The fix-up flow.** When a frozen signature turns out wrong after the groups have branched:
1. The group stops on that point and describes the change (which file, which signature, why) to the F0 owner; it never edits the frozen file in its branch.

## 6. Non-goals and ambiguities

### 6.1 Non-goals for 3.0.0

- The shared Library, per-listener feed keys, Apple Podcasts and key links.
- Server-side listening positions (P3), Plays/Finished renaming and Up Next.
- Passkeys, a TOTP enrolment UI, password change or reset in the UI, a user management UI and e-mail.
- Per-IP throttling, and a global login rate limit beyond the argon2 limiter (§1.5).
- Serialising archive admission per owner (the overshoot is up to one Episode per parallel job, §3.5).
- Reassigning Feeds automatically when the auth mode changes (§3.3).
- Deleting the legacy `engine/` settings keys (a later release, §2.2).
- An MCP tool for `me` or quota; any tool that takes a `user_id`.
- Admin management of other users' Cookie files, Defaults or API keys.
- Moving Feeds between users in the UI (only `copycast users reassign`).
- Counting Scratch, Postgres or the Feed cache in quotas; deleting anything for quota.
- A quota estimate for RSS enclosures (`enclosure length` is not parsed); direct fetches estimate 0.
- ffmpeg-as-downloader inside the fetch guard (unchanged from 2.3.0).

## 7. Rollout, and the test users on 3.dufour.xyz

The user asked (2026-11-05) for the server's config file to be provisioned with **two users and sample passwords for testing**, to be replaced later. Constraints:

- **Not before the 3.0.0 image.** 2.3.0's `AuthSettings` has `extra="forbid"`: an `[[auth.users]]` table or `default_quota` key would stop the running 2.3.0 api and worker at startup (exit 2). The file can be **prepared** next to the compose file (for example `config/copycast.toml.3.0`) but is moved into place in the same step that bumps `COPYCAST_IMAGE` to 3.0.0.
- **Sample passwords are long and random**, because the host is internet-facing: `openssl rand -base64 18` (24 characters) for each. They are reported to the user once, flagged "replace later", and are never written to the repository, the memory or a log.
- **Hashes are generated by the 3.0.0 image.** Its `ENTRYPOINT` is `["tini", "--", "copycast"]` (`Dockerfile:115`), so the subcommand follows the image name directly: `docker run --rm -i $COPYCAST_IMAGE users hash-password --stdin`. The TOML file holds `$` safely. Never put a hash in `.env` or compose YAML (`$` interpolation).
- **TOTP:** the base URL is https, so the Admin needs a `totp_secret`: `docker run --rm $COPYCAST_IMAGE users totp florent`. The otpauth URI and QR are handed to the user. The Member gets none.
- **The file holds secrets** (the Admin's `totp_secret` is one; the hashes are offline-attackable). The container runs as user `copycast`, uid and gid 1000 (`Dockerfile:64`, `--user-group`). So: `chown root:1000 config/copycast.toml && chmod 0640 config/copycast.toml`; the `config/` directory `0750 root:1000`. Keep the file out of git and out of any backup shared with others.

The file (`/opt/x.dufour.xyz/copycast.dufour.xyz/config/copycast.toml`, mounted read-only at `/config`; the image already sets `COPYCAST_CONFIG=/config/copycast.toml`):
```toml
[auth]
default_quota     = "10 GB"
session_days      = 30
owner_of_existing = "florent"      # every existing Feed and API key goes to florent

[[auth.users]]
username      = "florent"
password_hash = "$argon2id$…"      # sample password, to be replaced
totp_secret   = "…"                # generated at provisioning
admin         = true
quota         = "unlimited"

[[auth.users]]
username      = "emilia"
password_hash = "$argon2id$…"      # sample password, to be replaced
```

Steps:
1. **Back up**, with 2.3.0 still running:
   - `pg_dump -Fc` to `/root/copycast-backups/copycast-2.3.0.dump`;
   - `compose.yaml.bak-2.3.0` and `.env.bak-2.3.0`;
   - the Object store's `engine/` prefix, copied to `backup/engine-2.3.0/` in the same bucket with an S3 client on the `objects` network and the S3 keys from `.env`. 3.0 only copies these keys (§2.2), so this is a second line of defence, not the only one.
2. **Pre-checks:**
   - florent confirms that his podcast apps subscribe with the Feed URLs the UI shows (each Feed's own pair), not with the operator pair, which users mode no longer accepts on `/feeds` (§6.3);
   - the florent MCP key is noted (its prefix), to check it afterwards.
3. Make three changes to the server's own `compose.yaml`:
   - add the `./config:/config:ro` volume on the api and the worker;
   - remove `COPYCAST__AUTH__PASSWORD` from `x-env`;
   - remove it from `.env` too. The password and users rule is exclusive, so the api would otherwise refuse to start.
4. Write the file (permissions above), set `COPYCAST_IMAGE` to the 3.0.0 tag, then `docker compose up -d`. Whichever of the api and the worker migrates first, 0017 gives every Feed and key to `florent` (§2.1). The api and the worker **copy** `engine/defaults.json` and the Cookie files to `users/florent/`; the `engine/` keys stay.
5. Check:
   - `curl -u <pair>` on two Feeds and an enclosure HEAD (byte-identical URLs, D4);
   - `/api/me` 401 without a challenge;
   - login as florent with the TOTP code, and as emilia;
   - emilia sees only her empty "Copycast" Local feed;
   - the MCP key still works, as florent, and sees florent's Feeds;
   - no `auth.removed_owner_has_feeds` warning in the api log;
   - then watch for `Overcast/1.0` 401s for two hours.
6. **Replacing the test users later:**
   - a new password is a new hash (`users hash-password`) and `docker compose up -d --force-recreate api worker`. **The restart signs out every session of that user** (§1.5), so nobody who signed in with a sample password keeps access;
   - a new TOTP secret works the same way;
   - renaming `florent` is a new user: add the new `[[auth.users]]` entry, set `owner_of_existing` to the new name (startup refuses an `owner_of_existing` that names no configured user, so it must change before `florent` is removed), restart, then `docker compose stop worker`, `docker compose exec api copycast users reassign florent <new>` (it needs `WORKER_LOCK`), `docker compose start worker`, and finally remove `florent` and restart;
   - removing `emilia` leaves her Local feed as "owner removed" for Admins, and startup warns about it.

**Rollback to 2.3.0** (only if 3.0.0 misbehaves; changes made under 3.0 are lost):
1. `docker compose stop api worker`.
2. Restore the database into a fresh one (2.3.0 refuses a schema at 0017, and `--clean` alone would leave 0017's new tables behind): `dropdb copycast && createdb -O copycast copycast && pg_restore -d copycast /root/copycast-backups/copycast-2.3.0.dump`, run in the Postgres container.
3. The `engine/` keys are still in place (3.0 copies only); if they were changed by hand, restore them from `backup/engine-2.3.0/`.
4. Restore `compose.yaml.bak-2.3.0` and `.env.bak-2.3.0` (this brings back `COPYCAST__AUTH__PASSWORD` and drops the `/config` mount), and move `config/copycast.toml` aside: 2.3.0 refuses `[[auth.users]]`.
5. Set `COPYCAST_IMAGE` to the 2.3.0 tag and `docker compose up -d`.
